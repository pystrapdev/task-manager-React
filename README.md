# Daymark · React + MySQL

A responsive task dashboard with a Node.js API and MySQL storage. One deployment serves both the React website and `/api` routes. Tasks and projects are shared between browsers and survive application restarts.

## Deploy on CWeb / Node hosting

Use Node.js **24**. The frontend uses React and Vite; the included Node server serves both the built website and the API. Upload this project's contents, including `server`, `scripts`, `src`, `public`, `package.json`, `package-lock.json`, `vite.config.mjs`, `index.html`, and `tsconfig.json`. Exclude `node_modules` and your local `.env`.

| Hosting setting | Value |
| --- | --- |
| Install | `npm ci --include=dev` |
| Build | `npm run build` |
| Start | `npm start` |

Create a **MySQL** database in your hosting platform, then set these environment variables in the application settings:

```env
DB_HOST=your-mysql-host
DB_PORT=3306
DB_NAME=your-database-name
DB_USER=your-database-user
DB_PASSWORD=your-database-password
DB_SSL=false
```

Use the exact hostname and port provided for connections **from your hosted application**. Do not use `localhost` unless the provider explicitly says the database is in the same container. Set `DB_SSL=true` if TLS is required. Certificates are verified; optionally provide the provider's CA certificate through `DB_SSL_CA_FILE` (a server filesystem path).

These variables belong on the server, never in React source files. `.env` is optional when your platform injects environment variables. The server honors `PORT` supplied by your platform and listens on `0.0.0.0` by default.

On startup, the server connects to MySQL and creates `daymark_projects` and `daymark_tasks` if they do not exist. The database itself must already exist. The database user needs CREATE, SELECT, INSERT, UPDATE, and DELETE permissions. Three default projects are created; **no sample tasks** are inserted. Startup fails with a sanitized diagnostic if the database cannot be reached.

This version requires Node hosting. Uploading only the React static build will not provide the API or database connection.

## Test the hosted database without a terminal

1. Visit `https://YOUR-SITE/api/health`. A successful check returns:
   ```json
   {"status":"ok","database":"connected","engine":"mysql"}
   ```
   This queries MySQL's task table on every request. It does not expose credentials.
2. Open the dashboard and create a uniquely named task.
3. Open the same site in an incognito window or another device. The task should appear.
4. Restart/redeploy the application through the hosting dashboard and check that the task remains.
5. If your provider has a database viewer, look in `daymark_tasks` for that task.

A green health response proves the app can query its configured database. Creating a task verifies write access. Seeing the row in your provider's database viewer confirms which database it used. If the health endpoint returns 503 or startup fails, check the hosting logs and the database host/port, credentials, permissions, TLS, and network access rules.

## Local development

Copy `.env.example` to `.env` and fill in a local or development MySQL database's credentials. Do not commit `.env`.

```sh
npm ci
npm run build
npm start
```

Open http://localhost:3000. For React live reload, keep the backend running on port 3000 and run `npm run dev` in a second terminal. Open http://localhost:5173; the development proxy forwards `/api` requests to the backend.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/health` | Live MySQL status |
| GET | `/api/workspace` | Tasks and projects |
| POST | `/api/projects` | Create `{name,color}` |
| POST | `/api/tasks` | Create `{title,description,project,priority,due,status}` |
| PATCH | `/api/tasks/:id` | Update one or more task fields |
| DELETE | `/api/tasks/:id` | Delete a task |

`priority`: Low / Medium / High. `status`: todo / progress / done. `due`: YYYY-MM-DD or an empty string. IDs are generated by the backend. Writes use parameterized queries. Duplicate project names, invalid data, missing tasks, and database failures return JSON errors. Status updates change only the status field; clients do not replace the entire database workspace.

The app shows saving and connection states, keeps dialogs open when writes fail, and provides **Refresh workspace** for changes made elsewhere. There is no silent browser-storage fallback. Export downloads the currently loaded workspace. The React and Angular apps use the same schema (`daymark_projects` and `daymark_tasks`). Configure the same database to share tasks, or a separate database for independent workspaces. This app never stores tasks in localStorage.

This is a shared database demonstration with **no login or per-user isolation**. Anyone who can access the app/API can read and modify its tasks. Use test data or restrict access at your hosting platform before using private information.

## Verification

```sh
npm test
npm run build
npm run test:e2e
```

Unit/HTTP tests cover validation, configuration, API behavior, and static serving. Browser tests require Google Chrome and use intercepted API fixtures to check desktop/mobile flows and failed writes; they do not prove a real MySQL connection.

For a real database test, use a dedicated test database and provide the same DB variables, then run:

```sh
RUN_MYSQL_TESTS=true node --env-file-if-exists=.env --test tests/mysql.test.mjs
```

This creates tables/default projects if needed, creates a uniquely named test project/task, reconnects through a new pool, checks persistence/update/delete, and removes its test records. Without `RUN_MYSQL_TESTS=true`, this test is explicitly skipped.
